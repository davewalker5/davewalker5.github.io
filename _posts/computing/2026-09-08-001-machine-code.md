*Or: there are considerably easier ways of making a computer print 42*

A few days ago I wrote about finding what I called the **ZX80 spirit** in my RC2014. The important part wasn't really the ZX80 itself: It was the feeling of working with a computer where very little sits between the program and the machine:

- A processor
- Some memory
- BASIC
- Assembly language
- A few pieces of hardware

And the ability to ask:

> **What can I make this thing do?**

This morning, apparently, the answer was:

> **Pretend it is 1979**

## Six Bytes

It started with an extremely small Z80 assembly-language program.

```asm
ORG 0F000H
LD A,42
LD (0F100H),A
RET
```

Its purpose is hardly revolutionary: It loads the value `42` into the Z80 accumulator, writes that value to memory address `F100`, and returns. Once assembled, the entire program is six bytes:

```text
3E 2A 32 00 F1 C9
```

That in itself is rather satisfying:

- The source code is short enough to understand
- The resulting machine code is short enough to inspect
- And every one of those bytes has an obvious relationship to what the processor is being asked to do

But then came the interesting bit.

## Turning Machine Code Into BASIC

One of the classic ways of distributing machine-code routines for early home computers was not necessarily to distribute a binary file: It was to print the bytes as numbers.

Usually lots of numbers.

A BASIC program could then contain something like:

```basic
1000 DATA 62,42,50,0,241,201
```

and use `READ` and `POKE` to place those values into memory.

Those six decimal numbers are exactly the same six bytes:

```text
3E 2A 32 00 F1 C9
```

just expressed in a form BASIC can conveniently read.

So the journey becomes:

```text
Z80 assembly
    |
    v
machine-code bytes
    |
    v
decimal numbers in BASIC DATA statements
    |
    v
READ and POKE
    |
    v
the same machine-code bytes back in RAM
```

It is wonderfully circular. And wonderfully old-fashioned.

## Why Would Anybody Do This?

There are considerably easier ways of making a computer print `42`. There are considerably easier ways of transferring a binary to an RC2014. There are certainly considerably easier ways of doing almost everything involved here.

But that isn't really the point.

> The attraction is that the whole process is visible.

I can write:

```asm
LD A,42
```

assemble it and see:

```text
3E 2A
```

I can convert those bytes into:

```basic
DATA 62,42
```

I can then watch BASIC read those values and put them into memory. And eventually I can tell the Z80:

> Start executing at `F000`

There are very few mysteries in that sequence.

## DATA, READ and POKE

I remember this style of programming from the era when computer magazines routinely contained pages of BASIC listings. Sometimes buried within them were mysterious sequences of numbers.

```basic
1000 DATA 62,42,50,0,241,201
```

The instructions would tell you to type them carefully. Very carefully. One wrong number and the machine-code routine might fail spectacularly or merely fail mysteriously, which was probably worse.

The BASIC part of the program would then contain a loop along the lines of:

```basic
FOR I=0 TO 5
READ B
POKE C+I,B
NEXT I
```

At the time, those numbers could feel almost magical but they were simply *machine code*. Unless you knew assembly language, though, the connection between the numbers and the processor executing them was largely invisible.

Recreating the process now is rather different:

- I can see the assembly source
- I can see the exact bytes the assembler produces
- I can see their decimal equivalents
- I can see precisely where BASIC places them in RAM

The magic disappears but, oddly, that makes the whole thing more interesting rather than less.

## A Small Modern Concession

I did draw the line at manually converting arbitrary binary files into decimal numbers. I am recreating 1979 - I am not trying to suffer unnecessarily!

So I wrote a small .NET utility called `MachineCodeConverter`. Its job is deliberately simple:

Give it a raw binary such as:

```text
3E 2A 32 00 F1 C9
```

and it produces:

```basic
1000 DATA 62,42,50,0,241,201
```

For larger binaries it simply continues generating numbered `DATA` statements and that removes the tedious bit without removing the interesting bit.

- The assembly still has to be written
- The binary still has to be understood
- The memory still has to be reserved
- BASIC still has to load the bytes
- And something still has to tell the processor to execute them

## Where Does the Code Actually Go?

This is also where the exercise became more interesting than I expected. It is easy to say:

> POKE the machine code into RAM.

The obvious next question is:

> **Which RAM?**

The RC2014 is already running Small Computer Monitor, BASIC is using memory and the monitor itself occupies memory. So blindly selecting an address and spraying machine code into it would be rather unwise.

For this example I chose:

```text
F000-F005   machine code
F100        result byte
```

But before doing that I needed to establish two boundaries.

- BASIC must stop allocating memory **below** the machine-code area
- The code must also remain **below** memory used by Small Computer Monitor

So there is effectively a window:

```text
BASIC             Machine code/Data           SCM
------ | -------------------------------- | ------
       F000                              FBFF
```

That is the sort of thing modern application programming generally does an excellent job of hiding but here it is part of the exercise. And I rather like that.

## Even Negative Addresses Make Sense Eventually

There was another pleasingly peculiar detail. The Z80 has a 16-bit address space:

```text
0000-FFFF
```

or:

```text
0-65535
```

But this version of Microsoft BASIC uses signed 16-bit values when addresses in the upper half of memory are supplied to `PEEK` and `POKE`. So address:

```text
F000
```

becomes -4096 and:

```text
F100
```

becomes -3840. At first sight:

```basic
POKE -4096,62
```

looks slightly deranged. It isn't.

`-4096` and unsigned `61440` describe the same 16-bit bit pattern.

Again, something initially mysterious becomes entirely comprehensible once the representation is exposed.

That seems to be becoming a theme.

## Calling the machine code

Getting the bytes into RAM is only half the problem. BASIC must then transfer execution to them. The Microsoft BASIC used by this particular SCM configuration provides the `USR` function for calling a machine-code routine.

So eventually the BASIC program performs:

```basic
R=USR(0)
```

The `0` is not the execution address. The actual address is configured through BASIC's `USR` jump vector. For this experiment that vector is temporarily pointed at:

```text
F000
```

- BASIC evaluates `USR(0)`
- The Z80 starts executing the six bytes stored at `F000`
- They write `42` to `F100`
- `RET` returns execution to BASIC
- BASIC then performs a `PEEK` of `F100`

And prints:

```text
RESULT = 42
```

That is an absurd amount of machinery for producing a two-digit number.

I was ridiculously pleased when it worked!

## But the 42 Isn't the Point

The result could have been almost anything. `42` is merely convenient and a gentle nod to _The Hitchiker's Guide to the Galaxy_.

The important thing is the path.

```text
 assembly
     ↓
 assembler
     ↓
  six bytes
     ↓
 BASIC DATA
     ↓
   READ
     ↓
   POKE
     ↓
    RAM
     ↓
    USR
     ↓
    Z80
     ↓
  result
```

Every stage is visible. Every transformation can be inspected. Every address matters.

There is something deeply satisfying about being able to account for the complete journey from a line of source code to a physical byte sitting in RAM and ultimately being interpreted by the processor as an instruction.

## The Opposite of Abstraction

Modern computing depends upon abstraction and that is overwhelmingly a good thing. I do not particularly want to think about CPU registers every time I write a web application. I don't want to manually allocate memory for ordinary software. I certainly don't want to enter compiled programs as sequences of decimal numbers.

But abstraction also means that much of what the machine is actually doing disappears beneath layers which are deliberately designed to make it disappear.

The RC2014 allows me to choose how many of those layers I want:

- I can write BASIC
- I can write assembly
- I can look at the machine code
- I can choose the address where that machine code lives
- I can put the bytes there myself
- And then I can jump directly into them

That doesn't make the RC2014 a more *capable* computer.

It makes it a more **visible** one.

## Back to the ZX80 Spirit

That brings me back to the previous Field Notes entry. I wrote then that what I increasingly enjoy about the RC2014 is the idea of:

> A computer as a comprehensible object

This little experiment feels like another expression of exactly that. The interesting part of early home computers wasn't simply that they were primitive.

Primitive computers can simply be frustrating.

The interesting part was that the machine was close enough to the surface that a curious user could keep digging:

- Start with BASIC
- Discover `PEEK` and `POKE`
- Discover memory addresses
- Discover machine code
- Discover assembly language
- Discover what those mysterious numbers in magazine listings actually represented

And eventually realise that the apparent boundary between "software" and "the computer" isn't really a boundary at all. It is a stack of understandable mechanisms.

## Why Retrocomputing?

I increasingly suspect that this is one of the things I enjoy most about retrocomputing. It isn't nostalgia for inconvenience.

- I do not miss unreliable cassette storage
- I do not miss typing pages of numbers from magazines
- I do not miss losing programs because I had forgotten to save them

And given the choice between manually converting several hundred bytes to decimal or letting my converter do it, the converter wins every time.

> What I do enjoy is **visibility**

A sufficiently simple computer allows me to understand quite a lot of what is happening from the program down to the processor. Not theoretically. Not as a diagram in a textbook. By actually doing it.

## 1979, Briefly

So I spent a very happy morning taking six bytes of Z80 machine code:

```text
3E 2A 32 00 F1 C9
```

turning them into:

```basic
1000 DATA 62,42,50,0,241,201
```

making BASIC turn them back into six bytes in memory, and finally asking the Z80 to execute them.

And eventually:

```text
RESULT = 42
```

appeared on the terminal.

Just as nature intended.

There are unquestionably easier ways of making a computer print `42`.

But none of them would have allowed me to spend a morning briefly programming as though it were 1979.

And that, I think, was rather the point.
